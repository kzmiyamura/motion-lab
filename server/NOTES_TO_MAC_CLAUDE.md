# ThinkCentre側Claude → Mac側Claude への申し送り

このファイルは、ThinkCentre（Windows・GPU無し・本番実機）で実際にパイプラインを動かした
Claude Code から、Mac側で設計・実装している Claude Code への技術メモです。
**手元（Mac / Apple Silicon）では観測しづらい、実機ランタイムでしか見えない所見と改善提案**を書きます。
事実ベースの検証ログは `REPORT_FROM_THINKCENTRE.md`（2026-07-29分）を参照。

---

## 1. P1: 背景の第三者が2人スロット検出を汚染している疑い（優先度：高）

検証動画 `2fda2815`（Lewis Barr On2 のスマホ画面録画）は、**背景の鏡に撮影者（第三者）が写り込んでいる**。
`analyze_pair.py` の計測結果でスロットのサンプル数が **slot0=120 / slot1=226 と大きく偏った**のは、
片方のスロットが手前のダンサーと背景の第三者の間で取り違えられている可能性が高い。

- **コード確認済み**: `analyze_pair.py` は `num_poses=2` で MediaPipe に2人までを取らせ、
  スロット割り当ては `sorted(persons, key=lambda p: p["hipX"])`（＝**左右位置のみ**）。
  **面積/中央性による人物選別が無い**ため、3人以上写ると MediaPipe が自前の信頼度で「手前ダンサー1人＋背景の第三者」を
  選んでしまうフレームが混じり得る。
- **提案**: `num_poses=3`〜`4` に上げて候補を多めに取り、**bbox面積が大きい上位2人**（または画面中央に近い2人）を
  ペアとして採用するフィルタを挟む。現状はMediaPipeが2枠に絞った結果をそのまま使うので、背景の人を弾く術がない。
- 副作用として、両者の SHR がともに ~1.6 に高止まりして拮抗した一因もこれの可能性。

## 2. P1: オクルージョン下の SHR が信頼できない → verdict の算出母集団を見直す（優先度：高）

`slot0 SHR=1.6318 / slot1=1.5904` と、**女性側（本来 Follower）まで SHR が 1.59 と高く出た**。
地上の真実は「男性＝右・肩幅広＝Leader」だが、ルールベースは差を検出できず拮抗＝実質ミス。

- **コード確認済み**: SHR 平均の累積（`stats[i]["sum"] += slots[i]["shr3d"]`）に **occlusionガードが無い**。
  `occluded = d < OCCLUSION_DIST(0.10)`（腰中点が近接）で2人とも検出できているフレームも、そのまま平均母集団に入る。
  → 腕を組む密着姿勢で肩幅・腰幅の3D計測が崩れたフレームまで verdict 用 SHR 平均に混入している。
- **提案**: ルールベース verdict に使う SHR 平均は、**`occluded=True` のフレームを除外した「クリーンフレーム」だけ**から取る。
  （`stats` 累積を `if not occluded:` でガードするだけでも効くはず。表示用の全体平均は別途残してよい）

## 3. P1: contested 判定が過検出気味（優先度：中）

1本の動画で contested が全体の ~70%（0:05〜0:27）。ここまで広いと「難しい瞬間の抽出」ではなく
「ほぼ全編が難しい」になり、キーフレームの選別性が薄れる & クリーンフレームが枯渇して verdict が出せない。

- **提案**: occlusion 閾値を見直すか、contested を「連続占有率が高すぎる場合は代表フレームのみ間引く」。
  実際キーフレームは6枚出たが、0:05〜0:27 の1区間から拾えているのは3枚程度で妥当な間隔ではある。
  ただし「動画の大半が contested」というのは、そもそもこの動画がルールベース向きでない指標としても使える。

## 4. 回転解析: 間引きが効いていない疑い（優先度：中・パフォーマンス）

`analyze_rotation.py` の結果、`fps≈42`・`detectedFrames 1246 / totalFrames 1324`。
**31.5秒動画をほぼフルフレーム（全1324枚）処理**しており、これが所要 **約2分20秒（≈実時間4.4倍）** の主因。

- 一方 P1 の `analyze_pair.py` は 10fps 間引き済みで、より長い処理内容でも ~76秒と速い。
- **提案**: 回転解析も 10fps（または回転速度計測に必要な最小fps）へ間引けば、CPU実機で体感が大きく改善する。
  回転角の時系列は10fpsでも十分追える（1回転あたり十数サンプル取れる）。

## 5. 実機パフォーマンスの目安（timeout / UX チューニング用）

このThinkCentre（CPUのみ・Heavyモデル）での実測:

| 処理 | 動画長 | 所要 | 対実時間 | 間引き |
|---|---|---|---|---|
| 回転解析(rotation) | 31.5s | 約2分20秒 | ≈4.4x | 無し（フルfps）|
| ペア解析(P1) | 31.5s | 約76秒 | ≈1.5-2x | 10fps |

- `JOB_TIMEOUT_MS=3600000`（1時間）は十分余裕。ただし数分の長尺動画×回転解析（フルfps）だと10分超もあり得るので、
  間引き導入（提案4）で安全域を広げたい。
- Mac（Metal/GPU）比では明確に遅い。「裏でしっかり」方針なら許容だが、UI側は必ず非同期ポーリング前提で。
